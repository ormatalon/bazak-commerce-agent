# Design V2 – Bazak Shopping Copilot

Goal: a more flexible copilot. Version 1 rejects products on small wording misses ("knives" vs "knife") and often returns nothing. Version 2 ranks instead of rejecting, and never returns an empty answer.

## Stages

1. **Index (once, at startup).** For each product, build two texts and embed each one: a \*\*title text\*\* (title, category, brand) and a \*\*description text\*\* (description, tags). At query time, the query is embedded once and compared with both; the product's score is a weighted sum, e.g. 0.6 × title similarity + 0.4 × description similarity. Why: the title says what the product is, while the description adds context (use, occasion, style) but also generic marketing filler, so keeping it separate stops the filler from blurring what the product is. The weight is tuned on the eval set. Embed it with a local multilingual model from Hugging Face (e.g. `multilingual-e5-small`), so Hebrew queries match English products and no OpenAI model besides `gpt-6-luna` is used. Cache the vectors to disk next to the catalog.
2. **Parse.** The LLM extracts the intent, a short English query text for the embedding, and only the hard limits the user actually stated (price, rating), plus sort, count and mode. The query text is a \*\*list\*\*: one entry for a clear request, several for a vague one ("a gift for my mother" → "perfume", "jewellery", "handbag"). Each entry is embedded and ranked separately, and the best product from each direction gives the 3 diverse cards. The prompt lists the catalog's categories, so the directions stay within what the store sells. The parser can also return a list of likely categories, each checked against the real slugs; they act as a \*\*soft boost\*\* in ranking, never a filter, so a wrong guess only lowers a product's rank. Currency (kept from version 1): the model only reads the amount and the currency code (\`currency\`, null for dollars); code converts the price limits to dollars with the fixed, dated rate table in \`app/currency.py\` before the filter runs. The maximum is rounded down and the minimum up, so a converted budget is never exceeded. A currency with no rate gets one question asking for the budget in dollars.
3. **Filter.** Apply only the stated numeric limits. Keywords and category never filter, so wording can't empty the results. One exception, kept from version 1: \*\*exclusions\*\* the user states ("not leather") go in a separate \`exclude\` field and remove matching products in code, because embeddings handle negation poorly. The positive part alone becomes the query text.
4. **Rank.** Embed the query and rank the remaining products by similarity. Take the top candidates (10 here; 100, or a vector DB with metadata filters, at scale). Score = 0.6 × title similarity + 0.4 × description similarity + a small category boost (≈0.1) if the product is in a guessed category. A sort the user asked for ("cheapest", "highest rated") is applied to the relevant candidates. The relevance check runs on \*\*every card\*\*, not just the first: a card needs good similarity and a guessed category, weak ones are dropped, and the fallback fills any missing slots. Relevance uses three zones: \*\*strong\*\* similarity keeps the card whatever its category; \*\*borderline\*\* keeps it only if it is in a guessed category; \*\*weak\*\* drops it. So a wrong category guess only matters in the borderline zone. Thresholds are \*\*relative to each query\*\*, because absolute scores shift with query length and language: score the whole catalog for the query and measure how far a product stands above that query's average (a z-score). The two cut-offs are tuned on the eval set as labeled relevant/irrelevant pairs, choosing the values that separate them best (e.g. by F1).
5. **Fallback.** If the numeric filter leaves nothing, or the best ranked product fails a \*\*relevance check\*\* (low similarity, or outside the categories the parser guessed), treat it as "nothing fits". Keep the product type and loosen the stated limit instead: "laptop under $1,000" with no such laptop shows the cheapest laptops just above $1,000 and says so, never a tablet. If nothing is relevant even with no limits ("a gaming console"), the reply says the store doesn't carry it and suggests the closest category.
6. **Respond.** For a clear request, show the best cards. For a vague one ("a gift for my mother"), always show the 3 most likely products, explain why they may fit and what is uncertain, and ask one follow-up question (her age, her tastes). The answer refines the next round. If a budget was converted, the reply opens with it in the user's own term ("3,000 NIS is roughly $948"), written by code, not the model.

## Key decisions

- **Filter first, then rank.** Ranking the top 10 and filtering afterwards can leave nothing if all ten are over budget.
- **Only stated numbers filter.** Embeddings understand meaning, not numbers, so price and rating limits stay hard filters. Everything about what the product is goes to the embeddings.
- **Local embedding model.** Bazak allows only `gpt-6-luna`, so OpenAI embedding models are out. Trade-off: a heavier install (PyTorch) and a model download on first run.
- **Currency is converted in code, not by the model.** Same as version 1: the arithmetic is repeatable and testable, and the rates are a snapshot like the catalog. Fixes over version 1: round the maximum down and the minimum up (V1 could go over budget), and echo the user's own currency term (NIS, ₪) instead of the ISO code.
